# ADR-002: Data model — 3 core tables plus audit, quarantine, and run tracking

## Context
The pipeline ingests ~10,000 user rows per CSV, crawls loan products daily, matches
users to products (~30,000 candidate pairs per run), and emails results. The schema
must make re-runs safe, bad data impossible in canonical tables, and the matching
funnel measurable.

## Options considered
1. Minimal: users / loan_products / matches only
2. Core tables + audit layer (batches, staging, quarantine, crawl_runs, match_runs, notifications)

## Decision & Why
Option 2. The core three answer "what data do we have"; the audit layer answers the
questions a reviewer or regulator actually asks: what happened to my file, why was my
row rejected, why did this user match this product, what did the funnel cost. The
Treasure Hunt metrics (pairs before/after each stage) live in match_runs and are
generated by the pipeline itself — measured, not claimed.

## Where it fails
- More tables = more moving parts; mitigated by FK/ON DELETE CASCADE and idempotent DDL.
- TEXT[] allowed_employment is denormalized; acceptable for 3 fixed values, normalize
  if the domain grows.
- NULL = unconstrained criterion is permissive by design; criteria_raw preserves the
  extracted source so missing fields are visible (Workflow A warns on them).
- No trigger-managed updated_at: writers (Python ingest, n8n) set it explicitly to
  keep write behavior visible to workflow authors.
